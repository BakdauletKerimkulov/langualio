# Spec: Глобальное ревью проекта — безопасность, архитектура, документация

Source: `ai_docs/CODE_REVIEW_2026-07-19.md` — полное сеньорское ревью Flutter-клиента, Supabase-бэкенда и документации.

## Цель

Закрыть находки ревью в порядке риска: сначала дыры, через которые утекают деньги и портятся данные пользователя, потом архитектурный долг, потом документация и тесты. По завершении: ни одно server-authoritative поле не пишется с клиента, платные вызовы Claude защищены ролью и атомарной квотой, Supabase не протекает выше data-слоя, `ai_docs/PROJECT.md` описывает реальность, а CI гоняет тесты бэкенда.

## Контекст

Приложение живое и рабочее, архитектура в целом здоровая: строгий feature-first, Riverpod полностью на codegen, репозитории возвращают доменные модели, GoRouter централизован. Проблема в другом: `ai_toolkit/` писался позже большей части кода, поэтому многие нарушения — это нарушения правил, которые в тулките уже прописаны, но до кода не доехали. Отсюда характер работ: это не переизобретение, а приведение существующего кода к собственным правилам.

Что важно понимать перед началом:

- **Клиент — недоверенная среда.** `anon key` лежит в APK, любой может дёргать REST API напрямую. Всё, что разрешает RLS, разрешено читеру, независимо от того, что показывает UI.
- **Сервис-ключ в Edge Function обходит RLS полностью.** Внутри функции база не защищает — проверки делает сама функция.
- **Эталон уже есть в проекте:** `supabase/migrations/20260514193920_word_quiz_security.sql` — правильная триада SECURITY DEFINER (`search_path` + auth guard + revoke/grant). На неё равняемся.

Полный список находок с путями и номерами строк — в `ai_docs/CODE_REVIEW_2026-07-19.md`.

## Требования

### Этап 1 — Критично: деньги и данные пользователя

- [ ] **R1. Закрыть `generate-word-entry` от не-админов.** Функция вызывает платный Claude API, но проверки роли в ней нет вообще, хотя спека `004-admin-panel-spec.md:101` её требует. Сейчас любой зарегистрированный пользователь может сжечь квоту. После `getUser(token)` проверять `user.app_metadata?.role === 'admin'`, иначе 403.
  *Проверка:* обычный пользователь получает 403, админ — 200.

- [ ] **R2. Сделать квоту атомарной и брать её до вызова Claude.** Обе edge-функции сейчас читают счётчик, потом делают долгий запрос к Claude, потом пишут `count + 1`. Два параллельных запроса читают одно значение — лимит обходится, инкремент теряется. Нужна RPC-функция `try_consume_quota(p_kind text, p_limit int) returns boolean`, которая одним стейтментом инкрементирует с проверкой и возвращает, выдан ли «билет». Функция вызывается **до** обращения к Claude, `false` → 429. Решить и записать комментарием: возвращаем ли билет, если Claude ответил ошибкой.
  **Реализация:** `user_daily_usage` имеет отдельные колонки `message_count` и `generation_count`. RPC использует `CASE p_kind WHEN 'message' THEN ... WHEN 'generation' THEN ... END` для выбора колонки — без изменения схемы таблицы.
  *Проверка:* 10 параллельных curl при лимите 5 → ровно 5 успешных.

- [ ] **R3. Убрать у клиента запись в таблицу лимитов.** У `user_daily_usage` есть RLS-политики INSERT и UPDATE для владельца (`001_initial_schema.sql:179-181`). Хотя клиентский код не пишет в эту таблицу напрямую (обе edge-функции используют service role), уязвимость в другом: любой может отправить `PATCH /rest/v1/user_daily_usage` с anon key + JWT и обнулить себе `message_count`, полностью обойдя защиту R2. Оставить только SELECT (пусть видит свой остаток), писать — только сервис-ключом из функции.
  *Проверка:* `update user_daily_usage set message_count = 0` от роли `authenticated` падает.

- [ ] **R4. Перенести определение уровня на сервер.** `assessment_repository.dart:16` — клиент сам пишет себе `cefr_level` и `assessment_completed`. Уровень определяет, какой контент человек получает; сейчас его можно проставить любым. Нужна RPC `complete_assessment(p_answers jsonb) returns json`: сервер сам считает результат и выставляет уровень. RPC возвращает `{cefr_level: int, assessment_completed: bool}` — клиент показывает результат из ответа RPC вместо локально вычисленного. У клиента отобрать право писать эти колонки (column-level grant на `profiles`).
  **Предпосылка:** банк вопросов теста сейчас локальный. Мигрировать вопросы в таблицу `assessment_questions` (read-only, seed-миграция). RPC принимает `[{question_id: uuid, answer: text}, ...]`, сверяет с ответами на сервере. Обновить `assessment_repository.dart` на вызов `.rpc('complete_assessment', ...)`.
  *Проверка:* прямой `update profiles set cefr_level = 6` от пользователя падает; прохождение теста в приложении работает и показывает правильный результат.

- [ ] **R5. Проверить и стандартизировать model ID.** `chat/index.ts:5` использует `claude-sonnet-4-5-20241022`, а `generate-word-entry/index.ts:9` — `claude-sonnet-4-20250514`. Две функции используют разные модели. Сверить оба ID с актуальной документацией Anthropic, стандартизировать на один валидный ID, вынести в env-переменную или `_shared/` константу, покрыть smoke-тестом.
  *Проверка:* реальный запрос в чат возвращает ответ, а не 502; обе функции используют один и тот же model ID.

- [ ] **R6. Проверить секреты в репозитории.** Рядом с `.env.example` лежит `supabase/.env.local`. Убедиться, что он в `.gitignore` и никогда не попадал в историю (`git log --all -- supabase/.env.local`). Если попадал — ротировать service_role key немедленно, он даёт полный доступ к базе.
  *Проверка:* файла нет в индексе и в истории.

### Этап 2 — Важно: архитектура клиента

- [ ] **R7. Свести `core/` и `shared/` в один каталог.** Сейчас существуют две идентичные копии общих виджетов и констант, и обе реально импортируются (65 импортов против 20). Любая правка в одной копии молча расходится с другой. Оставить `core/`, `shared/` удалить, импорты переписать.
  *Проверка:* каталога `lib/src/shared/` нет, `flutter analyze` чистый.

- [ ] **R8. Убрать Supabase выше data-слоя.** Три места, где клиент базы протекает: `app_router.dart:41` и `admin_provider.dart:13` используют глобальный `Supabase.instance.client` мимо провайдера, а `onboarding_state_provider.dart:39,65` делает запросы `.from('profiles')` прямо в application-слое. Плюс `auth` — единственная фича без data-слоя: весь auth API вызывается из `auth_provider.dart`. Создать `AuthRepository`, остальное перевести на инъекцию через `supabaseClientProvider`.
  *Проверка:* `grep -r "Supabase.instance" lib/src --include="*.dart"` не находит ничего вне `data/` и bootstrap.

- [ ] **R9. Вынести `_mounted`-хак в один mixin.** Конструкция `try { state; return true; } catch (_) { return false; }` скопирована в 5+ нотифаеров (home, grammar, word_quiz, add_word, admin). Один mixin в `core/utils/`, все нотифаеры на него.
  *Проверка:* конструкция встречается в кодовой базе ровно один раз.

- [ ] **R10. Подключить `refreshListenable` в GoRouter.** Редиректы не переоцениваются при смене сессии: протухший токен или логаут не уводят пользователя на login до ручной навигации. `ai_toolkit/gorouter.md:62` требует `GoRouterRefreshStream` от auth-стрима.
  *Проверка:* при `signOut()` из любого экрана приложение само уходит на `/login`.

- [ ] **R11. Перестать молча терять прогресс.** `quiz_attempt_repository.saveAttempt` при ошибке только пишет в лог и продолжает — попытка пользователя исчезает бесследно. `chat_repository.fetchMessages:75` при ошибке возвращает пустоту, и человек видит «пустую историю» вместо ошибки. Пробрасывать в `AsyncError` (или ставить в retry-очередь для попыток).
  *Проверка:* при отключённой сети квиз показывает ошибку, а не делает вид, что сохранил.

## Вне рамок

- Переписывание рабочих фич без причины; новая функциональность.
- Миграция на другой стейт-менеджмент или архитектуру.
- Оптимизация производительности без замеров.
- Дизайн и UX-изменения.

## Критерии приёмки

- Ни одно server-authoritative поле (`cefr_level`, `current_xp`, `level`, `streak_days`, счётчики квот) не записывается с клиента — проверено негативными тестами от роли `authenticated`.
- Платные функции защищены ролью и атомарной квотой; параллельные запросы не пробивают лимит.
- `grep "Supabase.instance" lib/src` — только data-слой и bootstrap.
- `flutter analyze`, `flutter test`, `supabase db reset`, SQL-тесты и `deno test` зелёные в CI.
- `ai_docs/PROJECT.md` соответствует коду: каждая таблица и функция описана, несуществующего не описано.

## Риски

- **R4 и R7 — самые инвазивные.** Смена контракта ассессмента и удаление половины импортов затрагивают много файлов; делать отдельными коммитами, не смешивая с другими пунктами. R4 дополнительно меняет UX: результат теста теперь приходит от RPC, экран результатов должен парсить ответ RPC вместо локального вычисления.
- **R3: клиент не пишет в `user_daily_usage` напрямую** (проверено: 0 импортов в `lib/`), поэтому удаление RLS-политик INSERT/UPDATE не сломает приложение. Но до удаления убедиться, что edge-функции уже используют `try_consume_quota` RPC (R2), иначе старый код перестанет работать.
- **R14 трогает `auth.users`** — тестировать только на локальном стеке, в проде проверять на тестовом аккаунте.
- Этап 1 стоит выпустить отдельным релизом, не дожидаясь остальных: это дыры, а не долг.
- **Порядок деплоя Этапа 1:** (1) деплой миграции с новыми RPC (`try_consume_quota`, `complete_assessment`) + новые таблицы — старые политики остаются; (2) деплой обновлённых edge-функций, использующих новые RPC; (3) деплой миграции, убирающей старые INSERT/UPDATE политики на `user_daily_usage` и column grants на `profiles`. Нельзя деплоить (3) до (2) и (2) до (1).
